# IPC_Camera 项目分析报告

## 一、项目概览

| 项目项 | 分析 |
|---|---|
| 项目名称 | `IPC_Camera` |
| 项目类型 | 嵌入式网络摄像机设备端工程 + PC/平台 SDK + AI 算法集成工程 |
| 目标平台 | 海思 `Hi3516CV610` IPC 设备，Linux/musl ARM 环境 |
| 核心价值 | 完成摄像机音视频采集、编码、预览、录像、AI 检测、告警、协议接入、设备配置、升级与平台对接 |
| 目标用户 | IPC 固件开发者、设备集成商、平台/NVR/SDK 调用方、运维管理系统 |

从代码看，项目不是单一程序，而是一套完整 IPC 固件业务栈。设备端主程序位于 [stream_main.cpp](E:/Code/IPC_Camera/Hi3516/hi3516_ipc/main_app/stream_main.cpp:1)，公共能力位于 `Hi3516/share/ipc_share`，第三方与板级库位于 `Hi3516/ipc_platform/lib`，SDK 位于 `SDK/af_sdk`。

主要运行态流程：

```mermaid
flowchart TD
    A[stream 主进程] --> B[配置初始化]
    B --> C[视频 VI/VPSS/VENC]
    B --> D[音频 AI/AO/AENC/ADEC]
    C --> E[RTSP/RTMP 推流]
    D --> E
    C --> F[AI_APP 算法检测]
    F --> G[事件/告警]
    G --> H[WebSocket/TVSDK/ONVIF/GB28181/MQTT]
    B --> I[控制任务 CTaskManage]
```

## 二、技术栈分析

| 分类 | 技术 |
|---|---|
| 主语言 | C / C++，C 标准 `C11`，C++ 标准 `C++17` |
| 构建 | CMake 3.12+，部分第三方/板级库仍使用 Makefile |
| 媒体平台 | 海思 MPP：VI、VPSS、VENC、AI、AO、AENC、ADEC、IVE/SVP |
| 网络协议 | WebSocket、HTTP/HTTPS、RTSP、RTMP、ONVIF、GB28181/SIP、MQTT、SNMP、UPnP |
| 数据存储 | SQLite3 + JSON/INI 配置文件 |
| AI 能力 | YOLO、Face、HVF、人头、宠物、垃圾检测、音频异常等 |
| 安全/加密 | OpenSSL、GmSSL、GB35114、HTTP Digest/Basic、证书管理 |
| 日志 | `dlog` / `zlog` / SDK 内部 `NetSdkLog`，文件大小滚动 |

构建标准在 [ipc.cmake](E:/Code/IPC_Camera/Hi3516/hi3516_ipc/ipc.cmake:1) 中体现：

```cmake
set(CMAKE_C_STANDARD 11)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -Wall -fPIC")
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Wall -fPIC")
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -Werror=format -Werror=return-type")
```

技术选型理由推断：这是资源受限的嵌入式视频设备，C/C++ 与海思 MPP 是性能和硬件访问的必然选择；CMake 负责模块编排；SQLite/JSON 适合本地轻量持久化；ONVIF/GB28181/RTSP 是安防摄像机的主流互联协议。

## 四、核心业务逻辑

### 1. 主启动流程

`stream` 进程初始化顺序很清晰：

1. 初始化信号与日志。
2. 初始化全局配置。
3. 初始化视频流。
4. 初始化音频流。
5. 初始化推流模块。
6. 初始化控制管理模块。
7. 进入主循环，收到 `SIGINT/SIGTERM` 后逆序释放。

对应代码逻辑简化如下：

```cpp
bool initModules()
{
    CConfigManager::instance()->init();
    CStreamVideo::instance()->init();
    CStreamAudio::instance()->init();
    CPushStream::instance()->init();
    ControlManage::instance()->init();
    return true;
}
```

### 2. 视频链路

视频模块的核心链路：

```text
Sensor/VI -> VPSS -> VENC(main/sub/jpeg)
              |
              +-> AI VPSS Channel -> AI_APP
```

`CStreamVideo::init()` 中完成：

- `streamSys_init()` 初始化 MPP 与 VB 池。
- `streamVi_init()` 初始化视频输入。
- `streamVpss_init()` 初始化 VPSS。
- `streamVenc_init()` 初始化主码流、子码流、JPEG 抓图通道。
- 线程 `get_vencStream()` 获取编码帧并送 RTSP/RTMP/录像。
- 线程 `get_vpssStream()` 抽帧送 AI。

### 3. 音频链路

音频链路：

```text
AI/MIC -> AENC -> RTSP/RTMP/录像
AO/Speaker <- ADEC <- 对讲/广播
```

支持 AAC、G711U、G711A、PCM，G726 当前按设备画像可能关闭。

### 4. AI 业务

AI_APP 按配置动态创建算法实例，典型算法包括：

| 算法 | 业务 |
|---|---|
| `CMotionDetect` | 移动侦测 |
| `CHideDetect` | 遮挡/场景遮挡 |
| `CAudioDetect` | 音频异常 |
| `CSceneChangeDetect` | 场景变更 |
| `CHVFDetect` | 人/车/脸、越界、入侵、徘徊、停车 |
| `CPeopleHeadDetect` | 人员聚集、人员密度 |
| `CFaceDetect` | 人脸抓拍、人脸库、人脸比对 |
| `CGarbageDetect` | 垃圾暴露、垃圾满溢，按 `CAP_AI_GARBAGE_DETECT` 开关启用 |

动态绑定模式示例：

```cpp
if (stAlgoConfig.nEnMotionDetect) {
    bindVideoSlot<CAlgorithm>(
        m_StreamHandler.get(),
        m_pMotionAlgo.get(),
        &CAlgorithm::recvMediaData
    );
}
```

## 六、API 接口设计

项目同时存在多套接口：

| 接口类型 | 实现 | 说明 |
|---|---|---|
| WebSocket JSON | `CWebServer` / `CWebSslServer` | Web 插件/本地 UI 与控制进程交互 |
| HTTP SDK | `SDK/af_sdk/sdk_server` | 对外 SDK HTTP API |
| C SDK | `NetTVSDKServer.h` / `NetTVSDKClientInterface.h` | C 风格 SDK 接口 |
| ONVIF SOAP | `protocols/onvif` | 标准 ONVIF 发现、媒体、设备、事件 |
| GB28181/SIP | `protocols/gb28181` | 国标平台接入、RTP/PS 媒体 |
| MQTT | `platform_manager` / `mqtt_sdk_gateway` | 运维/平台对接，部分按能力宏启用 |

HTTP SDK 核心端点来自 [NetTVSDKHttpUrl.h](E:/Code/IPC_Camera/SDK/af_sdk/sdk_share/include/NetTVSDKHttpUrl.h:1)：

| 端点 | 方法 | 功能 |
|---|---|---|
| `/TVAPI/V1.0/Basic/Login` | POST | 登录并创建 Session |
| `/TVAPI/V1.0/Basic/Logout` | POST | 注销 |
| `/TVAPI/V1.0/Basic/KeepLive` | GET | 保活 |
| `/TVAPI/V1.0/Device/GetInfo` | GET | 获取设备信息 |
| `/TVAPI/V1.0/Device/Capability` | GET | 获取能力集 |
| `/TVAPI/V1.0/Device/GetDevConfig` | GET | 获取配置 |
| `/TVAPI/V1.0/Device/SetDevConfig` | POST | 设置配置 |
| `/TVAPI/V1.0/Replay/GetUrl` | POST | 获取回放地址 |
| `/TVAPI/V1.0/Event/AlarmListen` | GET | 长连接监听报警 |

WebSocket 请求/响应统一使用 `ActionCode`：

```json
{
  "ActionCode": 2100,
  "UserName": "admin",
  "Data": {}
}
```

响应：

```json
{
  "ActionCode": 2100,
  "DeviceName": "TV-3852T",
  "UserName": "admin",
  "Return": 0,
  "Data": {}
}
```

鉴权机制：

- SDK HTTP：支持 HTTP Basic 与 Digest，Digest 默认质询，算法 MD5。
- TVSDK 服务端：启动时注入管理员用户名/密码。
- WebSocket：通过 `AC_LOGIN`、在线用户 ID、权限字段做业务鉴权。
- ONVIF：使用 gSOAP `http_da` 摘要认证插件。

## 十、工程实践

亮点：

- 主流程初始化/反初始化顺序较清楚。
- 大量使用单例管理设备级资源，符合嵌入式服务常驻模型。
- 视频通道处理器、NAL 解析器使用策略模式。
- AI 算法实例按配置动态创建，减少不必要资源占用。
- SQLite 写入使用事务，部分路径有备份数据库。
- 设备能力通过画像宏集中定义，比散落的型号判断更可维护。
- 日志采用按大小滚动，适合嵌入式存储限制。

风险点：

| 风险 | 说明 |
|---|---|
| 单例过多 | 生命周期、测试隔离和并发状态较难控制 |
| 字符串 SQL 仍较多 | 部分表名/条件拼接需持续审计注入和转义问题 |
| 明文敏感信息 | `MQTT_PASSWORD`、平台 code、默认密码等写在头文件中 |
| 默认账号 | `admin` / `admin@123` 逻辑仍存在，发布版需强制初始化改密 |
| `system()` 调用 | ONVIF 中有 `system("route add ...")`，需限制输入与执行条件 |
| WebSocket 仅绑定 `127.0.0.1` | 推断前面还有 CGI/Web 代理；需确认外部访问边界 |
| 自动化测试不足 | 回归主要依赖人工/设备联调 |

## 十一、亮点与建议

### 亮点

1. 设备画像设计值得保留  
   `DEVICE_TYPE` + `CAP_*` 能把型号差异收口，避免业务代码到处判断型号。

2. 控制命令总线清晰  
   `ActionCode -> CTaskManage -> Task::CTask -> Business` 是项目最重要的扩展机制。

3. 媒体链路与业务控制基本解耦  
   音视频采集编码在 `main_app/stream_media`，配置和协议在 `ipc_share/control/protocols`。

4. AI 接入方式灵活  
   通过 `SignalSlot`/绑定回调把媒体帧分发到算法实例，支持按配置热启停。

### 改进建议

| 优先级 | 建议 |
|---|---|
| 高 | 移除或加密代码中的默认密码、MQTT 密码、平台 code |
| 高 | 给升级包校验增加签名验证、版本回滚策略、完整性校验记录 |
| 高 | 为 HTTP/WebSocket/TVSDK 增加统一权限校验矩阵 |
| 中 | 将 SQL 表结构迁移到显式 schema/migration，减少隐式建表 |
| 中 | 给 `ActionCode` 建立文档或自动生成接口表 |
| 中 | 增加 SDK HTTP 的接口测试和设备端任务分发单测 |
| 中 | 梳理 `new/delete/malloc/free` 混用问题，尤其视频帧结构分配释放 |
| 低 | 将大文件 `tvsdk_callbacks.cpp` 拆成设备、音视频、网络、事件、升级等子模块 |

性能建议：

- AI 送帧当前约每 10 帧处理一次，这是降载策略；建议配置化。
- RTMP/RTSP 双推时需要统计每通道队列积压、丢帧率、编码延迟。
- SQLite 高频写入建议按业务统一批量提交策略。
- 对长连接 `AlarmListen` 已设置线程池和 keep-alive，建议压测多客户端并记录内存。

## 十二、总结

整体评价：这是一个较完整的商用 IPC 设备端工程，覆盖采集、编码、预览、录像、智能分析、告警、协议接入、SDK、升级和运维。工程规模大，模块边界基本可辨，核心架构以“媒体管线 + 控制任务总线 + 多协议适配 + 本地配置/数据库”为主。

技术债务主要集中在安全配置硬编码、自动化测试不足、单例全局状态较多、部分大文件职责过重。后续维护建议优先围绕三件事推进：安全凭据治理、接口/命令码文档化、关键业务的自动化回归测试。这样这套工程会从“能跑的设备固件”更稳地走向“可长期演进的产品平台”。
